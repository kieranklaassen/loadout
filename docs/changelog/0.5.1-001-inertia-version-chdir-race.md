## Instructions

The Inertia asset-version lambda calls `ViteRuby.digest` on every request.
`ViteRuby.digest` computes inside `ViteRuby::Config#within_root`, which is
`Dir.chdir(root) { ... }` — and block-form `Dir.chdir` is **process-wide**. Ruby
permits only one active chdir block per process, so when two Puma threads are
inside it at once the second raises:

```
RuntimeError: conflicting chdir during another chdir block
```

and that Inertia request returns 500. vite_ruby's own 1-second memo narrows the
window but never closes it (the first request after boot is always unmemoized),
and the memo is itself read and written without synchronization.

Symptom to look for: intermittent 500s on Inertia requests under concurrency,
with `conflicting chdir during another chdir block` in the logs. It needs a thread
to yield the GVL mid-block, so it shows up under load rather than in testing —
one fleet app saw 2 × 500 out of 40 concurrent `X-Inertia: true` requests.

1. In `config/initializers/inertia_rails.rb`, replace:

   ```ruby
   config.version = -> { ViteRuby.digest }
   ```

   with:

   ```ruby
   # The lock is load-bearing. ViteRuby.digest computes inside
   # ViteRuby::Config#within_root, which is `Dir.chdir(root) { ... }` — and
   # block-form Dir.chdir is PROCESS-WIDE. A second thread entering while the first
   # is inside raises "conflicting chdir during another chdir block", so under Puma
   # two concurrent Inertia requests 500. vite_ruby's own 1-second memo narrows that
   # window without closing it, and is itself read and written unsynchronized.
   #
   # development/test recompute on every call, so a rebuilt frontend still
   # invalidates client history. Everywhere else the watched files cannot change for
   # the life of the process (a rebuild ships a new container), so the first digest
   # is memoized and no later request pays for the glob + SHA1 again.
   vite_digest_lock = Mutex.new
   vite_digest = nil

   config.version = lambda do
     vite_digest_lock.synchronize do
       next ViteRuby.digest if Rails.env.local?

       vite_digest ||= ViteRuby.digest
     end
   end
   ```

   Keep whatever comment already sits above the assignment explaining why the
   version is a lambda — the new comment extends it rather than replacing it.

2. If your app does not serve assets through `vite_ruby`, skip this entry
   entirely — there is nothing to guard.

3. If your app deploys in a way that rebuilds the frontend **in place** without
   restarting the Ruby process (unusual; Kamal and Docker-image deploys do not),
   drop the memoization and keep only the lock:

   ```ruby
   config.version = -> { vite_digest_lock.synchronize { ViteRuby.digest } }
   ```

   Otherwise keep the memoized form — it removes a per-request directory glob plus
   a SHA1 of every watched file from the hot path.

4. Add the regression test at `test/initializers/inertia_version_thread_safety_test.rb`.
   It must drive the configured lambda through `InertiaRails.configuration.version`
   — not a hand-rolled copy — or it proves nothing about the initializer. The
   collision is intermittent in the wild, so force it: park one thread inside the
   real `Dir.chdir` block while a second arrives.

   ```ruby
   # frozen_string_literal: true

   require "test_helper"

   class InertiaVersionThreadSafetyTest < ActiveSupport::TestCase
     setup { reset_vite_digest_memo! }

     test "a second thread is held off while the first is inside vite_ruby's chdir block" do
       inside_chdir = Queue.new
       release_error = nil

       with_slow_within_root(inside_chdir, hold_for: 0.2) do
         first = Thread.new { InertiaRails.configuration.version }
         inside_chdir.pop

         second = Thread.new do
           InertiaRails.configuration.version
         rescue RuntimeError => e
           release_error = e
           nil
         end

         first_digest = first.value
         second_digest = second.value

         assert_nil release_error,
           "a concurrent Inertia version read hit the process-wide chdir race: #{release_error&.message}"
         assert_equal first_digest, second_digest
         assert_match(/\A[0-9a-f]{40}\z/, first_digest)
       end
     end

     private

     # Holds the first caller inside the real chdir block so a second thread
     # provably overlaps it. Only the dwell time is manufactured — the
     # RuntimeError, when it comes, is raised by Ruby's own chdir bookkeeping.
     def with_slow_within_root(signal, hold_for:)
       config = ViteRuby.config
       original = config.method(:within_root)
       held = false
       guard = Mutex.new

       config.define_singleton_method(:within_root) do |&block|
         original.call do
           first = guard.synchronize { held ? false : (held = true) }
           if first
             signal << :inside
             sleep hold_for
           end
           block.call
         end
       end

       yield
     ensure
       config.singleton_class.send(:remove_method, :within_root)
     end

     # vite_ruby memoizes for one second; a warm memo returns before reaching
     # Dir.chdir, which is where the race lives. Guarded so a gem rename weakens
     # sensitivity instead of erroring.
     def reset_vite_digest_memo!
       builder = ViteRuby.instance.builder
       return unless builder.instance_variable_defined?(:@last_digest_at)

       builder.instance_variable_set(:@last_digest_at, nil)
     end
   end
   ```

## Verify

- `bin/rails test test/initializers/inertia_version_thread_safety_test.rb` is green.
- It is genuinely load-bearing: temporarily restore `config.version = -> { ViteRuby.digest }`,
  re-run, and confirm it fails with `conflicting chdir during another chdir block`.
  Restore the fix afterwards.
- `bin/rails runner 'puts InertiaRails.configuration.version'` prints a 40-character
  SHA1.
- `bin/rails test` is green.
