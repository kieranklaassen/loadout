# Pattern Survey Summary

Twelve of Kieran Klaassen's Rails projects (cora, atelier, tada, diskman, lifegarden, thinkroom, riffrec-dashboard, kieranklaassen-com, leva, every, erf-rails, blazer-ai) were surveyed across 9 pattern areas — stack choices, Inertia/React setup, auth, Kamal deployment, background jobs, testing, CI, `.claude`/`CLAUDE.md` conventions, and shared house libraries — to find what compound-stack-rails should ship as its default template. This doc synthesizes the 9 detail docs in this directory into one scannable reference. Six apps (atelier, tada, diskman, thinkroom, riffrec-dashboard, kieranklaassen-com) built in roughly the last 6 months form the "modern cohort" that nearly every recommendation below is drawn from; older apps (cora, lifegarden, every, erf-rails) and gems (leva, blazer-ai) mostly show what predates the convention or doesn't apply.

## What compound-stack-rails should adopt

| Area | Decision | Rationale |
|---|---|---|
| **Stack** | Ruby 3.4.2, Rails ~> 8.1.3, SQLite + solid_cache/solid_queue/solid_cable, propshaft, npm (package-lock.json), Tailwind v4 via @tailwindcss/vite, Kamal pinned `~> 2.12.0` | All 6 newest greenfield apps independently converged on this exact combination; it's Rails 8's own default plus the house Kamal pin rationale (shared kamal-proxy floor). |
| **Inertia/React** | `app/frontend` + `vite_rails`/vite-plugin-ruby + React 19 + TypeScript, snake_case pages mirroring `controller#action`, `createInertiaApp({ pages: '../pages' })` shorthand, base `InertiaController < ApplicationController` carrying `inertia_share`, SSR wired but off by default (with the shared `Net::HTTP` timeout patch) | Unanimous across the 6 modern apps; snake_case + base controller is majority convention; SSR-ready-but-off costs nothing and both real SSR apps hit the same gem gap independently. |
| **Auth** | Rails 8 generator pattern: `has_secure_password` + DB-backed `Session` model + `cookies.signed.permanent[:session_id]`, bcrypt 72-byte guard baked in, OmniAuth as opt-in account-linking not primary login, no open registration by default | The de facto house standard for every from-scratch Rails 8 app (Tada/Diskman near-identical concern code); Devise only survives in the older Jumpstart-Pro lineage this template doesn't need to inherit. |
| **Kamal deployment** | ERB-templated `deploy.yml` reading `ENV.fetch("KAMAL_...")` with no defaults (fail loud on missing env), `minimum_version: 2.12.0` pinned, kamal-proxy + ghcr.io + SQLite (`WEB_CONCURRENCY: "1"`) + `asset_path: /rails/public/vite` + thruster on port 80, single `web` role with an opt-in second role, `/up` healthcheck | Proven across 4 real shared-host deployments; the no-default env pattern is the only shape that has actually prevented a tenant config leak on the shared Hetzner host. |
| **Background jobs** | Solid Queue as ActiveJob backend, shared `config/queue.yml` shape (`threads: 3`, `processes: JOB_CONCURRENCY`, `polling_interval: 0.1`), `config/recurring.yml` with a mandatory hourly `SolidQueue::Job.clear_finished_in_batches`, `SOLID_QUEUE_IN_PUMA: true` by default with commented-out `job:` role, drop `whenever`/`schedule.rb` entirely | The entire Rails 8 + Kamal cohort uses it; needs no extra infra beyond the DB Kamal already provisions; `whenever` appears everywhere as an untouched stub, never actually used. |
| **Testing** | Minitest + fixtures, `inertia_rails/minitest` for Inertia assertions, Vitest + Testing Library for frontend, `parallelize(workers: :number_of_processors)` with documented override cases, Capybara/Selenium system tests and VCR/WebMock as opt-in modules | 11/12 projects use Minitest+fixtures (only the legacy pre-Inertia app uses RSpec/FactoryBot); a majority of newer apps skip system tests, so they shouldn't be mandatory scaffolding. |
| **CI** | GitHub Actions 3-job skeleton (scan_ruby, lint with rubocop cache, test) plus a JS check job (`npm run check`/typecheck + npm audit), `bundler-cache: true`, SHA-pinned actions, Vite pre-build before tests | Present near-verbatim in 4+ projects; SHA-pinning and Vite pre-build are documented fixes for real problems (supply-chain risk, autoBuild race flakiness) worth carrying forward by default. |
| **.claude/AGENTS.md** | `AGENTS.md` as the real file, `CLAUDE.md -> AGENTS.md` symlinked; seed `docs/solutions/` with the house YAML-frontmatter convention (module/tags/problem_type); lightly-seeded root `CONCEPTS.md`; template `config/deploy.yml` on `KAMAL_SERVICE`/`KAMAL_IMAGE`/`KAMAL_HOSTS` | The cleanest, most repeated convention among actively-maintained apps; avoids the two-file-drift problem cora has; the only Kamal shape proven across three real shared-host deployments. |
| **House libraries** | `ruby_llm` pinned `~> 1.16` as a first-class default with an initializer modeled on lifegarden's (ENV/credentials fallback, `use_new_acts_as`, `ActiveSupport::Notifications` chat-logging subscriber); `leva` and `riffrec` as optional/pinned-SHA add-ons, not defaults; skip `rails_js_logger` entirely | ruby_llm is in 7/9 active apps; leva is barely adopted (1/12, half-wired); riffrec is real but not universal; rails_js_logger has zero prior art in any of the 12 repos. |

## Open questions / divergence

- **TypeScript package manager and version drift.** All modern apps use npm + package-lock.json, but TS versions range from stable `^5.7` (atelier) to bleeding-edge `^7.0.2`/`^6.0.3` (tada, riffrec-dashboard, thinkroom, kieranklaassen-com) with no consistent target — worth picking one version deliberately rather than copying whichever app was surveyed last.
- **Session storage: DB-backed `Session` model vs. plain signed cookie.** Tada/Diskman/Riffrec-dashboard use a `Session` AR model (enables per-device sign-out); Thinkroom uses a bare `session[:user_id]` cookie. Both are recent, deliberate choices in actively maintained apps — the survey recommends the DB-backed model but this isn't unanimous.
- **SSR: fully on (kieranklaassen-com), selectively on per-controller (thinkroom), or off (everyone else).** No consensus on when SSR earns its complexity; the template should ship it wired-but-off and let individual apps opt in, rather than asserting a "correct" default.
- **Second Kamal role for background work.** diskman and lifegarden always run a dedicated job role; tada only renders one conditionally (credential-gated); thinkroom/riffrec-dashboard/kieranklaassen-com run zero. No clean single answer — genuinely depends on whether an app has real background-job needs at launch.
- **Alba/Typelizer typed serialization.** Used only by cora (1/8 Inertia apps) — worth reconsidering as the template matures, but too thin a sample to default to now. Everyone else hand-writes prop hashes and (where present) hand-writes matching TS types.
- **`.claude/` custom agents/commands/hooks.** Fully built out only in cora; absent or empty everywhere else. Genuinely unclear whether this is "not yet adopted" or "not worth it" — no second data point either way.
- **Postgres vs. SQLite, and Redis vs. no Redis.** Only lifegarden runs Postgres (as a Kamal accessory) among the modern cohort; diskman uses Valkey alongside SQLite for a fiber-based job runner. SQLite-first is the clear majority default, but any app with genuinely concurrent-writer needs will diverge — the template should document the escape hatch rather than pretend SQLite fits everything.
- **CI test-DB approach for Rails 8 apps with multiple SQLite databases** (primary/cache/queue/cable) — diskman explicitly tests for the presence of all 4 database files in a dedicated CI job; no other project does this. Worth considering as a template default given Solid Queue/Cache/Cable are also defaults, but it's currently a 1-project pattern.
